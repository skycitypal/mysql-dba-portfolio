# MySQL 运维与性能诊断实践

在自己电脑上搭的一个 MySQL 实例，用来练 DBA 真正要做的事：巡检、定位问题、建库造数、调优。

不追求把功能做全，追求每一句话都能查证。报告里出现的每个数字，都能在 `evidence/` 里找到对应的原始输出。

## 秒懂

我拿只读查询把本机 MySQL 的版本、参数、运行状态、数据量全查了一遍，再拿配置文件和错误日志去对，查出三个真问题：

1. 慢查询日志开着，但阈值设成了 10 秒，实际等于没开。实例连续跑了 3 天 21 小时，一条慢查询都没记下来。
2. 配置文件里写的是 8 个缓冲池实例，服务器实际用的是 1 个，错误日志里连个提示都没有。
3. 表名大小写的设置只能在初始化时定死，以后改不了。这个库要是迁到 Linux 就会出问题。

还有一个看着像问题、但我没下结论的：缓冲池只给了 128 MB，而这台机器有 16 GB 内存。我没直接说「内存不够」，因为这个实例几乎是空的，池子里只用掉不到 14% 的页。得先把数据造出来，再看这个数字才算数。

## 关于 AI 参与

这个项目是我在 AI（DeepSeek Harness）指导下做的。它帮我规划路线、讲原理、点评我贴回去的结果、整理文档。

数据库操作都是我自己在终端里敲的，报告里的数字来自真实运行，不是抄文档也不是编的。走错的弯路和被推翻的假设都留在文档里没有删——包括我一开始只读配置文件就下错结论那次。

把这件事写清楚，比藏着更好。能看懂、能复现、能回答「这个数字怎么来的」，比假装全是我独立想出来的实在。

## 已交付

### 环境清点报告 → [docs/00-环境清点.md](docs/00-环境清点.md)

七个只读查询，覆盖实例身份、主机资源、运行状态、数据量、关键参数。交叉验证之后拿到三个确证问题：

| 问题 | 关键证据 |
|---|---|
| 慢日志事实上失效 | 连续运行 3 天 21 小时，`Slow_queries = 0`，慢日志文件整段时间没被写过 |
| 配置与生效值不一致 | `my.ini` 写 `instances = 8`，运行时是 `1`，错误日志里没有任何告警 |
| 表名大小写不可逆 | 该变量只在初始化实例时可设，之后无法更改 |

报告第五节还留了三条被推翻的假设。翻车的地方不删，下次才不会重走。

### 巡检 SQL

`sql/00_env_check.sql` 做环境清点，纯只读，可以直接拿去用。
`sql/00b_env_check_round2.sql` 逐项对照配置文件里写的和实际生效的，就是对上面第二个问题做的。

写这两个脚本时踩到一个坑：子查询别名用了 `reads`，撞上 MySQL 保留字导致 `ERROR 1064`。后来学会用 `information_schema.KEYWORDS` 在自己服务器版本上查保留字，比翻文档靠谱。
