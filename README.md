# MySQL 运维与性能诊断实践

本项目在一台本地 MySQL 实例上完成数据库运维的日常练习，内容包括环境巡检、问题定位、
业务库建设与数据生成、索引与参数调优。项目不以功能完整为目标，重点在于：报告中出现的
每一个数值，都能在 `evidence/` 目录下找到对应的原始执行输出。

## 秒懂

使用只读查询对本机 MySQL 的版本、参数、运行状态与数据量做了完整清点，并与配置文件、
错误日志交叉核对，发现三个确实存在的问题：

1. 慢查询日志处于开启状态，但阈值设置为 10 秒，实际未能起到记录作用。实例连续运行三天
   二十一小时，没有记录到任何一条慢查询。
2. 配置文件中写入 8 个缓冲池实例，服务器实际生效值为 1，错误日志中没有任何相关提示。
3. 表名大小写规则只能在初始化实例时确定，之后无法修改。该库如需迁移到 Linux 会因此出现问题。

另有一项疑似问题，目前尚未下结论：缓冲池配置为 128 MB，而本机内存为 16 GB。没有直接判定
为内存不足，原因是该实例几乎没有负载，缓冲池中仅使用不到 14% 的页。需要先生成数据，
这个指标才有参考价值。

## 已交付

### 环境清点报告

[docs/00-环境清点.md](docs/00-环境清点.md)

共七个只读查询，覆盖实例身份、主机资源、运行状态、数据量与关键参数。交叉验证后得到三个
确证问题：

| 问题 | 关键证据 |
|---|---|
| 慢日志实际失效 | 连续运行 3 天 21 小时，`Slow_queries = 0`，慢日志文件在此期间未被写入 |
| 配置与生效值不一致 | `my.ini` 写入 `instances = 8`，运行时为 `1`，错误日志中没有任何告警 |
| 表名大小写规则不可逆 | 该变量仅在初始化实例时可设置，之后无法更改 |

报告第五节保留了三条被推翻的假设，供后续复盘时避免重走弯路。

### 巡检 SQL

`sql/00_env_check.sql` 用于环境清点，全部为只读操作，可直接使用。
`sql/00b_env_check_round2.sql` 逐项对照配置文件中写入的值与实际生效值，针对上述第二个问题编写。

编写这两个脚本时遇到一个问题：子查询别名使用了 `reads`，与 MySQL 保留字冲突，导致
`ERROR 1064`。此后改用 `information_schema.KEYWORDS` 在服务器自身版本上确认保留字，
比查阅文档更可靠。

## 如何复现

在 PowerShell 中执行：

```powershell
mysql -h 127.0.0.1 -P 3306 -u root -p --default-character-set=utf8mb4 -t < sql/00_env_check.sql
```

全部为只读操作，不会改动任何数据。

## 环境

MySQL 26.7.0 Community Server（Windows），存储引擎 InnoDB，字符集 utf8mb4，
二进制日志已开启。
