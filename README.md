# MySQL 运维与性能诊断实践

一个在自建 MySQL 实例上完成的数据库运维实践项目。目标不是再写一个"XX 管理系统"，
而是把 DBA 日常真正在做的事做出**可复验的证据**：

> **巡检 → 定位问题 → 建库造数 → 索引与参数调优**

所有结论都附**原始执行输出**（[`evidence/`](evidence/)），可以照 [`sql/`](sql/) 里的脚本
在自己的实例上复现。每个数字都能查到出处。

## 已交付

### 1. 数据库环境清点报告 → [`docs/00-环境清点.md`](docs/00-环境清点.md)

用 7 组只读查询覆盖版本、参数、运行状态与容量，并与配置文件、错误日志交叉验证，
得出 **3 个确证问题**：

| # | 问题 | 关键证据 |
|---|---|---|
| **P1** | `long_query_time = 10` 让慢查询日志**事实上失效** | 采集时实例已连续运行 3 天 21 小时，`Slow_queries = 0`，慢日志文件整个运行期**未被写入过** |
| **P2** | **配置文件与生效值不一致** | `my.ini` 写 `innodb_buffer_pool_instances = 8`，运行时实际生效 `1`，且错误日志**无任何告警** |
| **P3** | `lower_case_table_names = 1` 是**不可逆的跨平台迁移地雷** | 该变量**只能在初始化实例时设定**，之后无法更改；迁到 Linux（默认 0）会导致表名解析不一致 |

另有 **1 个待验证的优化项**：InnoDB buffer pool 仅 128 MiB（占主机内存 0.79%）。
——在造出真实负载之前**不下"内存不足"的结论**，只给出造数后回来对照的判定标准。

> 报告第五节还留档了 **3 条被推翻的假设**，包括我自己第一轮"只读配置文件就下结论"的错误。
> 走错的路也写下来，比只写结论有用。
