# 02 · 业务库设计

实操 1 的产出说明：业务场景、表清单，以及所有业务表都要遵守的字段与命名规范。

---

## 业务场景

一个小型电商订单系统。

选这个场景的理由：订单、订单明细、支付三张表基本能覆盖真实建模里最常见的问题 ——
一张主表、一张明细表、一张状态会反复流转的支付表，再加上客户和商品两个基础数据表。
数据量也容易造，适合后面做索引对比。

## 表清单

| 表名 | 一行代表什么 | 作用 |
|---|---|---|
| `t_customer` | 一个客户 | 下单的人 |
| `t_product` | 一个商品 | 卖的东西 |
| `t_order` | 一次下单 | 订单头，记录谁、什么时候下单、总共多少钱 |
| `t_order_item` | 订单里的一行商品 | 订单明细。一次买三种东西就有三行 |
| `t_payment` | 一次支付 | 一个订单可能有多条：失败重试、分次支付 |

数据量预期：`t_order_item` 会是最大的表，目标是十万行以上，用来做索引前后的对比。

---

## 通用规范

下面这些是所有业务表都要遵守的，写第一张表时就按这个来。

### 固定字段

| 字段名 | 类型 | 说明 |
|---|---|---|
| `id` | `bigint` | 主键。数据库内部使用的流水号 |
| `deleted` | `tinyint NOT NULL DEFAULT 0` | 软删标记。`0` 未删除，`1` 已删除 |
| `create_time` | `timestamp(6) NOT NULL` | 创建时间 |
| `update_time` | `timestamp(6) NOT NULL` | 更新时间，改动时自动刷新 |

**为什么用软删而不是 `DELETE`**：删掉的数据还能恢复，也留下审计痕迹。
代价是每个查询都要带上 `deleted = 0`，这一点在后面的索引设计里要一起考虑。

**为什么时间字段用 `timestamp(6)`**：带六位小数秒（微秒）。同一秒内发生多条记录时，
带上微秒才能排出先后顺序。

### 业务唯一标识

`id` 是数据库自己用的流水号，不适合对外。涉及外部系统对接、或者需要防重的表，
再加一列业务单号，例如 `order_id`、`payment_id`，类型 `varchar(64)`，并加**唯一索引**。

作用是让数据库兜底防重：应用层万一重复提交，唯一索引会直接拒绝，而不是写进两条脏数据。

### 命名约定

| 对象 | 约定 | 例子 |
|---|---|---|
| 表名 | `t_` + 业务模块 | `t_order`、`t_order_item` |
| 主键 | 统一叫 `id` | — |
| 唯一索引 | `uk_` 开头 | `uk_order_id` |
| 普通索引 | `idx_` 开头 | `idx_customer_ct` |

### 两条说明

**关于主键用不用自增**：本项目用 `bigint` + `AUTO_INCREMENT`，单机系统这样最省事。
分布式系统一般会换成雪花 ID 之类的方案，避免多库自增冲突 —— 这点记在这里，本项目不采用。

**关于 `USING BTREE`**：很多建表模板会在索引后面显式写它。InnoDB 的索引默认就是 BTREE，
本项目不重复写。

## 第一张表：`t_customer`

固定字段先给出，业务字段待补：

```sql
CREATE TABLE `t_customer` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键 ID',

  -- 业务字段待补，建议至少包含：
  --   客户登录名（或手机号）
  --   昵称
  --   邮箱
  --   状态

  `deleted` tinyint NOT NULL DEFAULT 0 COMMENT '删除标记: 0-未删除, 1-已删除',
  `create_time` timestamp(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) COMMENT '创建时间',
  `update_time` timestamp(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6) COMMENT '更新时间',

  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='客户表';
```

## 造数设计

数据生成器见 [`../sql/03_seed.py`](../sql/03_seed.py)，生成物 `03_seed_data.sql` 不入库（约 10 MB）。
灌数之后的验证见 [`../sql/03_seed_verify.sql`](../sql/03_seed_verify.sql)。

### 规模

| 表 | 行数 |
|---|---|
| `t_customer` | 5,000 |
| `t_product` | 1,000 |
| `t_order` | 20,000 |
| `t_order_item` | 约 52,000（每单 1～5 件，加权平均约 2.6 件）|
| `t_payment` | 约 19,000（成功的 + 少量失败重试）|
| 合计 | 约 98,000 |

### 四条约束

**一、`create_time` 必须显式写入。**
表上有 `DEFAULT CURRENT_TIMESTAMP(6)`。造数时不传这个字段，九万行会全部挤在同一秒，
索引页堆在同一个点上，测出来的性能和真实场景完全不符，后面所有索引对比都失去意义。
生成器把数据铺在过去两年内随机分布。

**二、金额必须对得上。**
`t_order.order_amount` 等于该订单所有明细的 `SUM(product_price * quantity)`；
`t_payment.amount` 等于对应订单的金额。数据自相矛盾的话，后面写汇总查询会得到无法解释的结果。

**三、分布要偏斜。**
真实业务里少数客户下大量单、少数商品是爆款。均匀分布会让索引的选择性看起来比实际更好，
测不出真实效果。生成器按权重抽样，靠前的客户 / 商品被抽中概率更高。

表内分布：

| 字段 | 分布 |
|---|---|
| `t_order.status` | 已完成 70%、已发货 12%、已支付 8%、待支付 5%、已取消 5% |
| 每单商品件数 | 1 件 20%、2 件 30%、3 件 25%、4 件 15%、5 件 10% |
| `t_customer.status` | 3% 禁用 |
| `t_product.status` | 10% 下架 |

**四、支付要有失败重试。**
约 5% 的已支付订单，会先有一条「支付失败」记录，再有一条成功记录。
真实系统里这是常态，也是 `payment_no` 唯一索引存在的意义：防止重复回调写进两条支付。

### 主键可预测

生成器先 `TRUNCATE` 五张表（子表在前），`AUTO_INCREMENT` 归零。主键因此从 1 开始连续分配，
客户 / 商品 / 订单的 ID 可以直接按 1..N 生成引用，不需要回查数据库。

### 灌数之后要 ANALYZE TABLE

InnoDB 的索引统计信息不是实时更新的。刚灌完数据时 `Cardinality` 可能仍是旧值甚至 0，
优化器会拿着过期信息选错索引。所以 `03_seed_verify.sql` 里有一句 `ANALYZE TABLE`，
强制立刻重新采样。

这也是运维上的常见动作：大批量导入之后，DBA 通常要手动跑一次 `ANALYZE TABLE`。
