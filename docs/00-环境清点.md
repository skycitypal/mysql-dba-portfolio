该实例在安全性方面的配置没有问题：二进制日志已开启，严格 SQL 模式已启用，每张表使用
独立表空间，崩溃恢复与日志回放所需的条件都已具备。

问题集中在可观测性方面，即无法判断哪里慢。慢查询日志处于开启状态，但阈值设置为 10 秒，

慢查询。慢日志文件中现有的少量内容来自上一次运行，本次运行期间没有写入。

配置文件中另有两处与实际情况不符。缓冲池实例数写入 8，实际生效值为 1，错误日志中没有

## 三、确证的真实问题（3 个）

### P1 · `long_query_time = 10` —— 慢日志等于没开

**现象**：`slow_query_log = ON`、`log_output = FILE`，看起来配置完备。

**证据**
- `Slow_queries = 0`，而 `Uptime = 337,520 s`（**3.9 天**）。
- 慢日志文件 `D:\MySQL\MySQL Server 26.7\Data\SOR-PC-slow.log` 仅 **1,570 字节**，
  且 mtime 是 **2026-10-07 01:04** —— **早于本次启动（10-08 02:57）**，即整个运行期没被写过。

**判据**：生产环境常用阈值 **0.5～1 s**。10 s 意味着任何 9.9 秒的查询都被放过，
而 9.9 秒在业务上已经是事故。**慢日志的价值在于"发现趋势"，不是"记录灾难"**。

**结论**：这不是"参数偏大"，而是**该功能事实上失效**。配置开关是开的，但阈值让它永远不触发。

**怎么修**（动态生效，无需重启）
```sql
SET GLOBAL long_query_time = 1;          -- 会话级另需 SET SESSION
```
持久化则改 `my.ini` 的 `long_query_time=1`。
另建议开 `log_queries_not_using_indexes=ON`（需配合 `min_examined_row_limit` 防止小表刷屏）——
它能把"没走索引"的查询也抓出来，这往往是慢查询的根因。
> 待第二轮确认：`log_queries_not_using_indexes` 与 `min_examined_row_limit` 的生效值。

### P2 · `my.ini` 与生效值不一致 —— 参数审计必须以运行时为准

**现象**：配置文件写 `innodb_buffer_pool_instances=8`（my.ini 第 271 行，位于 `[mysqld]` 段内），
但服务器实际生效值是 **1**。

**证据**
| 来源 | 值 |
|---|---|
| `my.ini` 第 271 行 | `innodb_buffer_pool_instances=8` |
| 运行时 `performance_schema.global_variables` | `innodb_buffer_pool_instances = 1` |
| `SOR-PC.err` 全文搜 `buffer_pool_instances` | **0 条匹配（连告警都没有）** |

**已排除的解释**
- ❌ 不是读错了配置文件：同一文件里的 `innodb_buffer_pool_size=128M`（生效 134,217,728 ✓）、
  `long_query_time=10`（✓）、`max_connections=151`（✓）、`server_id=1`（✓）、
  `lower_case_table_names=1`（✓）**全部逐项吻合** ⇒ 服务确实在读这个 my.ini。
- ❌ 不是 `mysqld-auto.cnf` 覆盖：datadir 根目录只有 `auto.cnf`（存 server UUID），**没有 `mysqld-auto.cnf`**。
- ❌ 不是运行时改的：`innodb_buffer_pool_instances` 是**只读启动参数**，运行期改不了。

**最可能的原因**：pool < 1 GiB 时服务器把实例数归 1。my.ini 自带的注释（第 247–249 行）也印证这个语义：
> *"When the size of the buffer pool is greater than 1GB, setting innodb_buffer_pool_instances to a value greater than 1 can improve the scalability on a busy server."*

⚠️ 这一步是**推断**，不是实测。要证实需做一次受控实验（把 pool 临时提到 ≥1 GiB 重启，看 instances 是否变成 8）——
记录在「后续完善方向」，不要在没做之前把结论写死。

**结论（这才是重点）**：**`my.ini` 是"请求"，不是"事实"。** 参数审计的唯一可信来源是
`performance_schema.global_variables`（或 `SHOW VARIABLES`）。任何基于配置文件的判断都可能出错 ——
本项目第一轮就栽在这里（见 5.1）。

---

### P3 · `lower_case_table_names = 1` —— 迁移地雷，而且**初始化后无法更改**

**现象**：`lower_case_table_names = 1`（表名以小写存储、比较不区分大小写）。

**判据**
- Windows/macOS 默认 1，Linux 默认 **0**。
- 值 `1` 时表名在磁盘上被强制小写。把库迁到 Linux（默认 0）后，
  `MyTable` 与 `mytable` 在源库是同一张表、在目标库是两张表 —— **迁移/主从跨平台必炸**。
- **关键**：`lower_case_table_names` **只能在初始化实例时设定，之后不可更改**。
  也就是说，**这个值现在不定，以后就只能重建实例**。

**结论**：不是性能问题，是**不可逆的架构约束**。若这个库将来要上 Linux 生产环境，
必须在建库之初就决定，而不是等出事。

**怎么处理**
- 短期（本项目）：**接受它**，但把它写进 README 的"已知限制"，并在作品集里把它作为
  「跨平台迁移 checklist」的一条 —— 这正好是面试加分项。
- 长期：若确定要迁 Linux，需在目标实例**初始化时就设 `lower_case_table_names=0`**，
  再逻辑导出/导入，不能直接拷数据文件。

## 四、待验证的优化项（1 个）

### O1 · InnoDB buffer pool 仅 128 MiB，占内存 0.79%

**证据**
- `innodb_buffer_pool_size` = 134,217,728 B = **128 MiB**（这是 MySQL 的**出厂默认值**，说明从未按机器调整过）。
- 主机物理内存 **16,296 MiB**；`128 / 16296 = 0.79%`。
- 专用数据库服务器的常见起点是可用内存的 **50%～75%**。

**⚠️ 为何当前不能判定为内存不足**
- 池中仅使用 **1,127 / 8,192 页 ≈ 17.6 MiB**（13.8%），`pages_dirty = 0` ⇒ 缓冲池远未填满。
- `Queries = 87`（3.9 天）⇒ 没有实际负载。
- 命中率 96.43% 由 **27,312 次逻辑读中的 974 次物理读**构成，这些读取绝大多数来自启动与
  后台线程，并非业务查询。

**结论**：这只能说明该配置从未按机器调整过，不能说明内存不够用。
必须先造出真实数据与负载，调优才有讨论的基础，这也是阶段 1 的目的。

**判定标准（造数后回来对照）**
- 命中率 **< 99%** 且 `Innodb_buffer_pool_pages_free` 长期接近 0 ⇒ 池偏小；
- 若造数后数据总量远小于 128 MiB，那么更大的池也不会带来任何收益 —— 此时正确的结论是
  **"这个实例不需要更大的 pool"**，而不是硬调。

## 五、被推翻的假设（留档，避免重走弯路）

### 5.1 ❌ 「`innodb_buffer_pool_instances=8` 配 128M 是教科书级反模式」

这是项目第一轮仅依据 `my.ini` 得出的结论，并不成立。
实测生效值为 **1**，服务器自行处理了该差异。真正的问题在于 P2（配置与生效值不一致），
参数本身并没有写错。

教训：`my.ini` 不等于事实，下结论前应先查询 `performance_schema.global_variables`。

### 5.2 ❌ 「`tmp_table_size=395M` 在 TempTable 引擎下是空操作」

该假设在写入文档之前即被推翻。`my.ini` 第 176–180 行的官方注释写明：
> *"Defines the maximum size of internal in-memory temporary tables created by the MEMORY storage engine and, **as of MySQL 8.0.28, the TempTable storage engine**."*

因此 `tmp_table_size` 对 TempTable 引擎同样生效，与 `temptable_max_ram=1G` 配合使用，并非空操作。
教训：应先读配置文件自带的注释，MySQL 写在 `my.ini` 里的注释即为官方文档。

### 5.3 ❌ 「buffer pool 命中率 96.43% 说明内存不足」

不成立。在该实例空载（`Queries=87`）、缓冲池仅使用 13.8%、脏页为 0 的情况下，
命中率反映的是启动阶段的磁盘读取，而非业务压力。空载实例的命中率不具备诊断价值。

## 六、参数审计方法论（本项目固化下来的做法）

1. **只信运行时**：`performance_schema.global_variables` / `global_status`，不信 my.ini。
2. **先换算单位**：MySQL 的参数大量以字节返回（如 `134217728`），须换算为可读单位后再作判断。
3. **交叉验证**：`Uptime` 与 error log 的启动时间、`pool_size / page_size` 与 `pages_total`，
   两两对得上才说明数据可信。
4. **区分"配置"与"负载"**：命中率、`Slow_queries` 这类指标在没有负载时不能作为证据。
5. **配置文件只用于回答"是谁改的"**，不用于回答"现在是什么"。

## 十、术语解释

报告里出现过的词，按出现顺序列一遍：

| 词 | 一句话 |
|---|---|
| 实例 | 一个跑起来的 MySQL 服务，可以理解成"一套数据库" |
| my.ini | MySQL 启动时读的设置清单，一个文本文件。上面写的值不一定就是实际生效的值 |
| 慢查询日志 | MySQL 把跑得太久的查询记下来的地方。多慢算慢，由 `long_query_time` 决定 |
| 阈值 | 就是"多慢算慢"的那个秒数 |
| 缓冲池 | InnoDB 把磁盘数据页缓存到内存的那块区域，是 MySQL 最吃内存的地方 |
| 页 | InnoDB 读写数据的最小单位，默认 16 KB |
| 命中率 | 要数据时在内存里直接找到的比例。找不到就得读磁盘，慢很多 |
| 实例数 | 把缓冲池切成几份，让多个线程各管一份，减少互相抢 |
| 生效值 | 服务器实际在用的值。和配置文件里写的不一定一样 |
| lower_case_table_names | 控制表名在磁盘上怎么存、比较时区不区分大小写。只能在初始化时设 |
| 二进制日志 | 记录所有改数据的操作，用来恢复到某个时间点，或做主从复制 |
| 严格模式 | 数据类型不合法时直接报错，不会偷偷把数据改成别的值 |
| 独立表空间 | 每张表一个数据文件，删表能真正把空间还给系统 |
| 只读查询 | 只查不改的 SQL，不会动数据 |
