# 课程 U1 · 索引

> **这一课你要拿到的东西**：知道索引是什么、为什么它能让查询变快、以及怎么从输出里看出
> MySQL 到底用没用上索引。
>
> 前置：U0（库 / 表 / 行 / 列、主键）。
>
> 这一课要用的材料是你自己跑出来的：`evidence/U0-index-lookup-output.txt`。

---

## 1.1 没有目录的图书馆

想象一本 500 页的书，你要找「海豚」出现在哪几页。

如果这本书**没有目录、没有页码索引**，你只能从第 1 页翻到第 500 页，一页页找。
有目录的话，你翻到「H」那一节，直接跳到第 187 页。

数据库的索引就是这张目录。

你上次跑的 `SHOW INDEX FROM actor`，看到的就是 `actor` 表的两张「目录卡片」。

---

## 1.2 没有索引时，MySQL 怎么查

叫**全表扫描**：从第一行读到最后一行，逐行判断是否符合条件。

回头看你上次跑的这条：

```sql
SELECT * FROM actor WHERE actor_id = 3;
```

它返回了 1 行。如果 `actor_id` 上没有索引，MySQL 要把 200 行**全部读一遍**，
才能确定「符合条件的只有这一行」。

`sakila.actor` 只有 200 行，所以快得感觉不出来。但把场景换成一张 100 万行的订单表，
每次按订单号查都读 100 万行，这就是慢查询最常见的来源。

---

## 1.3 索引长什么样

InnoDB（MySQL 的默认存储引擎）的索引默认是一种叫 **B+ 树** 的结构。

名字唬人，但核心就一件事：**把数据按某个顺序排好，做成多层目录。**

不是「目录 → 页码」这么一层，而是：

```
顶层目录：  [1000]  [5000]  [9000]
              ↓       ↓       ↓
中层目录：  [1200] [1500] [1800] ...
              ↓
具体数据页： 记录 1201、1202、1203 ...
```

因为**排过序**，每一层都能用「二分查找」快速缩小范围。100 万行数据，
大约比较 20 次就能定位到目标，而不是比较 100 万次。

这也顺带解释了两件事：

- 索引能加速 `WHERE`（按条件找）和 `ORDER BY`（顺序输出），因为数据本来就是有序的。
- 索引会让 `INSERT` 变慢，因为每插一行，目录也得跟着改，还得保持有序。

## 1.4 读你跑过的那两行

你上次的输出是这样（`evidence/U0-index-lookup-output.txt`）：

```
| Table | Non_unique | Key_name            | Seq_in_index | Column_name | Collation | Cardinality | ... | Index_type | ... |
| actor |          0 | PRIMARY             |            1 | actor_id    | A         |         200 | ... | BTREE      | ... |
| actor |          1 | idx_actor_last_name |            1 | last_name   | A         |         121 | ... | BTREE      | ... |
```

逐列拆开：

| 列 | 你看到的值 | 意思 |
|---|---|---|
| `Table` | actor | 索引建在 `actor` 表上 |
| `Non_unique` | 0 / 1 | 0 = 唯一索引（不许重复），1 = 普通索引（允许重复） |
| `Key_name` | PRIMARY / idx_actor_last_name | 索引的名字。`PRIMARY` 是主键自带的 |
| `Seq_in_index` | 1 / 1 | 在联合索引里排第几位。这两行都是单列索引，所以都是 1 |
| `Column_name` | actor_id / last_name | 索引建在哪一列上 |
| `Collation` | A | 排序方向。A = 升序，D = 降序 |
| `Cardinality` | 200 / 121 | 估算的**不重复值个数** —— 见下一节，这是重点 |
| `Sub_part` / `Packed` | NULL | 前缀索引、压缩索引，这里没用上 |
| `Index_type` | BTREE | 索引类型，就是 1.3 讲的 B+ 树（BTREE 是它的类别名） |
| `Visible` | YES | 对优化器是否可见 |
| `Expression` | NULL | 函数索引，这里没用上 |

所以你有两张目录卡片：一张按 `actor_id` 排（主键），一张按 `last_name` 排。

---

## 1.5 Cardinality：这两个数字是重点

`Cardinality` 是「这一列里**有多少个不同的值**」，由 InnoDB 采样估算得到。

| 列 | 总行数 | Cardinality | 意思是 |
|---|---|---|---|
| `actor_id` | 200 | 200 | 200 行，200 个不同的值 —— 每个都不一样 |
| `last_name` | 200 | 121 | 200 个演员，只有 121 个不同的姓（重姓） |

这个比值叫**选择性**（selectivity）：

```
actor_id  ： 200 / 200 = 1.000   ← 极其独特
last_name ： 121 / 200 = 0.605   ← 一般
```

**怎么用这个数**：

- 选择性越接近 1，索引越好用。因为「按这个值查」能一下子把范围缩到极少数行。
- 如果某一列的选择性很低（比如「性别」列，只有 2 个值），索引几乎帮不上忙：
  你查 `性别 = 男`，命中全表一半的行，MySQL 还不如直接全表扫描。

⚠️ 注意 `Cardinality` 是**估算值**，不是精确值。它来自采样统计，会有偏差。
感觉不准的时候可以执行 `ANALYZE TABLE 表名;` 让它重新统计。

## 1.6 预告：什么情况索引会白建

这一节先给结论，细节留到实操 3 用真实数据演示：

- 把索引列**包在函数里**：`WHERE YEAR(create_time) = 2026` —— `create_time` 上的索引用不上
- **类型不匹配**：列是字符串，你传数字，MySQL 隐式转换后可能用不上索引
- `LIKE '%关键词'` 前面带百分号 —— 没法利用排序，只能全表扫
- 反过来，查出来的行**占了全表很大比例**时，优化器会主动放弃索引，因为绕目录还不如直接扫

## 1.7 动手：亲眼看 MySQL 用没用索引

工具叫 `EXPLAIN`。它的作用是让 MySQL **说出它打算怎么执行这条查询**，但**不真正执行**。

```sql
USE sakila;
EXPLAIN SELECT * FROM actor WHERE actor_id = 3;
EXPLAIN SELECT * FROM actor WHERE last_name = 'CHASE';
EXPLAIN SELECT * FROM actor WHERE first_name = 'ED';
```

输出列很多，**只需要看三列**：

| 列 | 看什么 |
|---|---|
| `type` | 查找方式。`ALL` = 全表扫描，其他值都比它好 |
| `key` | 实际用了哪个索引。`NULL` = 一个都没用 |
| `rows` | MySQL 估计要检查多少行 |

预计你会看到：

- 第 1 条 `key = PRIMARY`，少到 `rows = 1` —— 走主键，最快
- 第 2 条 `key = idx_actor_last_name` —— 走普通索引
- 第 3 条 `key = NULL`，`type = ALL`，`rows = 200` —— **全表扫描，没有可用于 `first_name` 的索引**

**为什么第 3 条慢了你也感觉不到**：`actor` 只有 200 行，对 MySQL 来说是一瞬间的事。
要让索引的差别真正显现出来，数据量得到十万行以上 —— 这正是实操 1、2 要造数据的原因。

## 1.8 联合索引与最左前缀

> 这一节是建 `t_order` 时补上来的，因为单列索引不够用了。

### 一条索引可以建在多个列上

```sql
key `idx_customer_deleted_ct` (`customer_id`, `deleted`, `create_time`)
```

物理含义：先按 `customer_id` 排序；`customer_id` 相同的，再按 `deleted` 排；
`deleted` 也相同的，再按 `create_time` 排。

### 最左前缀原则

索引 `(a, b, c)` 只能从最左边那一列开始用。

| 查询条件 | 过滤能用吗 | 排序能用吗 |
|---|---|---|
| `WHERE a = ?` | 能 | — |
| `WHERE b = ?` | 不能（跳过了 a） | — |
| `WHERE a = ? ORDER BY b` | 能 | 能 |
| `WHERE a = ? ORDER BY c` | 能 | **不能**，要额外排序 |
| `WHERE a = ? AND b = ? ORDER BY c` | 能 | 能 |

### 为什么 `WHERE a = ? ORDER BY c` 排序用不上

假设索引 `(a, b, c)` 里 `a = 1` 这一段的数据是：

```
a=1, b=1, c=8
a=1, b=1, c=9
a=1, b=2, c=1
a=1, b=2, c=2
```

注意这个顺序本身是受约束的：索引内部靠 b 分块，每个块里 c 必须是升序。
所以 `b=1` 那两块是 8 再 9，反过来写就不成立了。

你要 `ORDER BY c`，期望 c 按 `1, 2, 8, 9` 出现。但顺着索引扫下来，拿到的 c 是 `8, 9, 1, 2`。

`a` 固定了，`b` 没固定。索引在 b 这一层还分块，块内的有序性出不了块。

MySQL 的处理方式：用索引找到 `a = 1` 的所有行（这一步省掉了全表扫描），
再把结果取出来**额外排一次序**。`EXPLAIN` 的 `Extra` 列会显示 `Using filesort`。

所以更准确的说法是「过滤能用、排序用不上」，而不是「索引完全没用」。

### 常见疑问：a 固定之后索引里所有 b 都在，为什么排序还是用不上

这是本项目学习过程中提出的问题，值得单独记一笔。

想法是：`a = ?` 之后剩下的行覆盖了所有的 b，索引里 b 和 c 都在，那排序总能用上吧。

关键在「块内有序」和「整体有序」的差别。索引保证的是每个 b 块内部 c 有序，
但块与块之间是断开重排的；而 `ORDER BY c` 要求整个结果集按 c 有序。两者不是一回事。

想让排序也吃到索引，就把 b 也固定住：

```sql
WHERE a = ? AND b = ? ORDER BY c     -- 过滤和排序都能用上
```

b 变成单一值之后只剩一个块，块内 c 本来就是升序的。

### 规则

等值条件列排在前面，排序（或范围）列紧接其后，中间不能被一个没被固定的列隔开。

### `deleted` 这种只有两个值的列为什么能放中间

`deleted` 只有 0 / 1，选择性极低，单独给它建索引没有意义。

但它如果是**等值条件**（`deleted = 0`），放进联合索引能减少回表次数，
而且不会破坏排序，因为等值条件把这一列固定成了单一值。

反过来，写成 `deleted > 0`（范围条件）就会把后面的有序性切断。

## U1 实测复盘（2026-10-16，你的真实输出）

原始记录：`evidence/U1-index-return01.txt`。三条 EXPLAIN 与 1.7 的预测逐条对上。

| 查询 | 结果 | 说明 |
|---|---|---|
| `WHERE actor_id = 3` | `Rows fetched before execution (rows=1)` | 主键等值查询被优化成常量，优化阶段就把结果取出来了，执行阶段不用再找 |
| `WHERE last_name = 'chase'` | `Index lookup on actor using idx_actor_last_name (rows=2)` | 用上了 `last_name` 的索引 |
| `WHERE first_name = 'ED'` | `Table scan on actor (rows=200)` + `Filter` | 全表扫描，读满 200 行再筛 |

**你拿到的是树格式，不是表格格式。** 新版 MySQL 把 `explain_format` 的默认值改成了 `TREE`，
旧版默认是 `TRADITIONAL`（就是有 `type` / `key` / `rows` 三列的表格）。树格式从最内层往外读，
缩进最深的那行最先执行。想要表格版：

```sql
EXPLAIN FORMAT=TRADITIONAL SELECT * FROM actor WHERE first_name = 'ED';
```

想确认本机的默认格式：

```sql
SELECT @@explain_format;
```

**第三条里两个 `rows` 值得看**：`Table scan` 那行是 `rows=200`（要读多少行），
`Filter` 那行是 `rows=20`（过滤后预计剩多少）。先读 200 行才筛出 20 行，多读的 180 行就是浪费。

**这份输出里踩到两个坑，是两回事**

一是**框线错位**（跟编码无关）。用 `-t` 时 MySQL 按「值的宽度」算边框长度，而树格式的 EXPLAIN
值里**本身带换行**（第三条的 `Filter` 有两行）。宽度算多了，补齐的空格被挤到下一行，
右框线就单独落了一行：

```
| -> Filter: (actor.first_name = 'ED')  (cost=20.2 rows=20)
    -> Table scan on actor  (cost=20.2 rows=200)
 |
```

**树格式不要加 `-t`。** 不加就没有框线，也不会错位。

二是**文件编码**（跟对齐无关）。PowerShell 5.1 的 `>` 重定向写出的是 **UTF-16**
（文件开头两字节是 `FF FE`）。记事本和 VS Code 能自动识别，所以打开看着是好的；
但 GitHub 网页、`grep`、`diff`，以及默认按 UTF-8 读文件的工具都会把文件当成二进制，读不出来。

存证据文件时用 `cmd /c` 包一层，拿到的是客户端原样的 UTF-8 字节：

```powershell
cmd /c "mysql -h 127.0.0.1 -P 3306 -u root -p --default-character-set=utf8mb4 < D:\mysql-dba-portfolio\sql\04_explain.sql > D:\mysql-dba-portfolio\evidence\04-explain-output.txt"
```

路径写全，是因为相对路径只在「当前目录恰好是项目根」时才成立。换个目录跑，输入文件找不到，
cmd 会报 `The system cannot find the file specified`。

**一个要留意的失败方式**：输入文件不存在时，`>` 仍然会创建一个 **0 字节**的目标文件
（cmd 退出码是 1，但文件看着像是生成了）。所以拿到输出文件先看大小，0 字节就是没跑成。
另外 `evidence\` 目录必须已经存在，cmd 不会替你新建目录。

## 术语解释

| 词 | 一句话 |
|---|---|
| 索引 | 数据的「目录」，让 MySQL 不用逐行翻找 |
| 全表扫描 | 从第一行读到最后一行 |
| B+ 树 | MySQL 索引的底层结构：排好序的多层目录 |
| 主键索引 | 主键自带的索引，`Key_name` 显示为 `PRIMARY` |
| 唯一索引 | 不允许重复值的索引，`Non_unique = 0` |
| 普通索引 | 允许重复值的索引，`Non_unique = 1` |
| 联合索引 | 建在两列或多列上的一个索引，顺序有意义 |
| 最左前缀原则 | 联合索引只能从最左那一列开始用，跳列就失效 |
| filesort | EXPLAIN 的 `Extra` 里出现，表示 MySQL 额外排了一次序，没吃到索引的有序性 |
| Cardinality | 估算的不重复值个数，越接近总行数越好用 |
| 选择性 | `Cardinality / 总行数` 的比值，衡量索引好不好用 |
| `EXPLAIN` | 让 MySQL 说出执行计划，但不真正执行 |
| `type` | EXPLAIN 里的查找方式，`ALL` 是全表扫描 |
| `key` | EXPLAIN 里实际使用的索引，`NULL` 表示没用索引 |
