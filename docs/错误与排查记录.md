# 错误与排查记录

学习过程中实际撞到的报错，每条记录四件事：报错原文、当时在做什么、根因、怎么改。

留这份记录的原因：报错原文往往直接指出线索，但「以为的原因」和「真正的原因」经常不是一回事。
下面六条里有两三处就是这种情况，也一并记下来了。

## E1 · 漏写 `-p` 不等于「提示我输密码」

```
ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: NO)
```

**场景**：重置 root 密码之后第一次登录。

**根因**：`mysql` 客户端不写 `-p`，含义是「用空密码连接」，而不是「弹出来问我要密码」。

**排查线索**：报错括号里那句 `using password: NO` 已经说明客户端根本没有发送密码。
如果是 `using password: YES`，那才是「发了密码但不对」。

**改法**：加上 `-p`。

## E2 · 报错说「需要安全连接」，先问自己这条连接算不算安全

```
ERROR 2061 (HY000): Authentication plugin 'caching_sha2_password' reported error:
Authentication requires secure connection.
```

**场景**：用 `--skip-grant-tables` 启动实例、改完 root 密码并执行 `FLUSH PRIVILEGES` 之后，
通过命名管道连接。

**根因**：`ALTER USER ... IDENTIFIED BY` 会把账号的认证插件设成 `caching_sha2_password`，
这个插件拒绝在非安全通道上传输密码，而命名管道不算它认可的安全通道。
在此之前能够免密登录，只是因为 `--skip-grant-tables` 根本不校验密码。

**改法**（两种都可行）：

- 连接时加 `--get-server-public-key`，用服务器的 RSA 公钥加密密码
- 或改用 TCP 连接。客户端默认 `--ssl-mode=PREFERRED`，会自动协商 TLS，之后再不用带参数

完整过程见 [`00-root-password-reset.md`](00-root-password-reset.md)。

## E3 · 别名撞上保留字

```
ERROR 1064 (42000) at line 17: You have an error in your SQL syntax; ... near
'reads,(select variable_value+0 as v from performance_schema.global_status where ' at line 2
```

**场景**：环境清点脚本里用两个子查询相除，计算 InnoDB 缓冲池命中率。

**根因**：子查询别名写成了 `reads`，`READS` 是 MySQL 的保留字，裸用作别名会语法错误。

**排查线索**：报错的 `near '...'` 部分直接给出了解析器停下的位置，正好是那个词。

**自查手段**：不用翻文档，在自己服务器上查保留字表：

```sql
SELECT WORD, RESERVED FROM information_schema.KEYWORDS WHERE WORD IN ('READS','R','Q','VAR');
```

`RESERVED = 1` 表示不能裸用作标识符。这张表给的是**当前服务器版本**的答案。

**改法**：别名换成 `r`、`q`。脚本见 [`../sql/00_env_check.sql`](../sql/00_env_check.sql)。

## E4 · PowerShell 的 `>` 写出来的是 UTF-16

**现象**：把 mysql 的输出用 `>` 存成文件，本机打开正常，推到 GitHub 后显示乱码；
用命令行工具读取时报「二进制文件」。

**场景**：保存环境清点和 EXPLAIN 的原始输出，作为报告的附件证据。

**根因**：Windows PowerShell 5.1 的 `>` 重定向默认写 UTF-16，文件开头两个字节是 `FF FE`。
记事本和 VS Code 会按这个标记自动识别编码，所以本机看着正常；GitHub 网页、
`grep`、`diff` 以及默认按 UTF-8 读文件的工具都不认。

**改法**：用 `cmd /c` 包一层做重定向。这样是字节直通，不经过 PowerShell 的编码转换。
路径写全，因为相对路径只在当前目录恰好是项目根时才成立：

```powershell
cmd /c "mysql -h 127.0.0.1 -P 3306 -u root -p --default-character-set=utf8mb4 < D:\mysql-dba-portfolio\sql\04_explain.sql > D:\mysql-dba-portfolio\evidence\04-explain-output.txt"
```

**附带的坑**：输入文件不存在时，`>` 仍然会创建一个 **0 字节**的目标文件，cmd 退出码是 1。
也就是说命令失败了，但目录下多了一个文件，看着像是跑成功。拿到输出文件先看大小。

## E5 · 表格框线错位，跟编码没关系

**现象**：EXPLAIN 的结果用 `-t` 输出时，边框对不齐，右框线单独占一行：

```
| -> Filter: (actor.first_name = 'ED')  (cost=20.2 rows=20)
    -> Table scan on actor  (cost=20.2 rows=200)
 |
```

**根因**：`-t` 按「这一列的值有多宽」来画边框，而树格式 EXPLAIN 的值**本身带换行**
（上面就是一个单元格里的两行）。宽度算多了，补齐的空格被挤到下一行。

**改法**：树格式不要加 `-t`。

**一条教训**：这个现象和 E4 的编码问题同时出现，我最初把它们归成同一件事，是错的。
两个症状同时出现时，先分别确认各自的成因。

## E6 · `-e` 的取值是紧跟其后的那一个参数

**出错的命令**：

```powershell
$sql = @'
explain format=traditional select * from actor where first_name = 'ED';
'@
mysql -h 127.0.0.1 -P 3306 -u root -p -e --default-character=utf8mb4 $sql
```

**现象**：

```
ERROR 1059 (42000): Identifier name 'explain format=traditional select * from actor
where first_name = 'ed';' is too long
```

`-e` 后面的 `--default-character=utf8mb4` 被当成了要执行的 SQL；真正的 SQL 变量 `$sql`
掉到位置参数上，被 mysql 客户端当成**数据库名**。服务器拿这串 SQL 文本去校验库名，
长度超过了标识符的 **64 字符**上限，于是报「名字太长」。

两个可以顺带记住的点：

- 报错是 1059「名字太长」，而不是 1049「库不存在」。因为长度检查先于查找发生。
  （这条我原先预期成 1049，实测推翻。）
- 报错里那串文本显示为全小写，与本机 `lower_case_table_names = 1` 的行为一致。

**根因**：`-e` 是一个带值的选项，它的值就是命令行里紧跟其后的那个参数。
命令里写成了 `-e --default-character=utf8mb4 $sql`，于是：

- 交给服务器执行的 SQL 是字符串 `--default-character=utf8mb4`
- `$sql` 落到位置参数的位置，mysql 把它解释成要连接的数据库名

**改法**：让 `-e` 后面紧跟 SQL。把它放到最后最省事：

```powershell
mysql -h 127.0.0.1 -P 3306 -u root -p --default-character-set=utf8mb4 -e $sql
```

**补充两点**：

- PowerShell **不会按空格拆分变量**。多行字符串作为变量的值传给程序时是一个参数，
  所以 `-e $sql` 不需要加引号。（这一点已实测：把一个含空格和换行的字符串传给程序，
  收到的参数个数是 1。）
- 这条命令还缺一步：`actor` 表在 `sakila` 库里。没有 `-D` 也没有 `USE` 时会报
  `ERROR 1046 (3D000): No database selected`。可以在 SQL 里先写一句，或者加 `-D sakila`：

  ```powershell
  mysql -h 127.0.0.1 -P 3306 -u root -p -D sakila --default-character-set=utf8mb4 -e $sql
  ```

## 附 · 三处「看着像错、其实不错」的判断

记下来是因为它们都被实测推翻了，而推翻的过程本身有价值。

**一、`--default-character` 少写 `set` 会报错——不会。**

实测 `mysql --default-character=utf8mb4 --help` 退出码为 0。MySQL 的选项解析接受长选项的
**无歧义缩写**，`--default-character` 能唯一对应到 `--default-character-set`。

不过仍建议写全。缩写只在当前没有歧义时成立，将来多一个同前缀的选项就会失效。
另外在 E6 那条命令里，这个选项根本没被解析，因为它被 `-e` 吃掉了。

**二、「`innodb_buffer_pool_instances=8` 配 128M 是反模式」——不是。**

这是只读配置文件就下结论造成的。运行时实际生效值是 `1`，服务器自己处理了。
真正的问题是「配置文件写的值和实际生效的值不一致」，详见
[`00-环境清点.md`](00-环境清点.md) 第二节。

**三、「框线错位是编码问题」——不是。**

见 E5。两件事同时出现，被我归成了一件。

**四、`comment'商品编号'` 中间少个空格会报错——没有。**

写商品表时误写成 `comment'商品编号'`（少一个空格），我当时的说法是「能不能省取决于词法解析器，
不用赌，补上」。实测这条建表是通过的：MySQL 在 `comment` 和 `'` 之间不需要空格，
因为引号不是标识符字符，扫描器会自然分词。

补空格仍然建议，但那属于风格一致，不是语法要求。
